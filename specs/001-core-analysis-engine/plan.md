# Implementation Plan: Core Analysis Engine

**Branch**: `001-core-analysis-engine` | **Date**: 2026-04-26 | **Spec**: [spec.md](spec.md)
**Input**: Feature specification from `specs/001-core-analysis-engine/spec.md`

---

## Summary

Build a local-only static analysis engine that accepts a filesystem path, detects which of 6 AI coding harnesses (Claude Code, GitHub Copilot, Codex CLI, Gemini CLI, Cursor, Windsurf) are present, classifies their kit files using a normalized vocabulary, maps cross-file relationships, and outputs a `KitGraph` JSON document (`nodes[]` + `edges[]` + `harnesses{}` index). New harnesses are added via declarative YAML definition files — no core code change required.

---

## Technical Context

**Language/Version**: TypeScript 5.x / Node.js 20 LTS
**Primary Dependencies**: `glob` (file traversal), `js-yaml` (harness definitions), `fast-glob` (pattern matching), `gray-matter` (frontmatter parsing)
**Storage**: Filesystem only — reads analyzed repo, writes JSON to stdout or file
**Testing**: Vitest (unit + integration), with fixture repos per harness
**Target Platform**: Cross-platform CLI (Windows, macOS, Linux) via Node.js
**Project Type**: CLI tool + importable library
**Performance Goals**: < 5s for 500-file repos; < 200ms for typical 50-file workspace
**Constraints**: Zero network calls; zero code execution from analyzed repo; skip files > 1 MB
**Scale/Scope**: Up to 500 files per repo in v1; 6 first-class harnesses + generic fallback

## Implementation Phases

### Phase A — Foundation (engine skeleton + 1 harness)

1. Initialize TypeScript project (`package.json`, `tsconfig.json`, `vitest.config.ts`)
2. Implement `HarnessDefinition` schema and `loader.ts`
3. Implement Detection Pass (`detector.ts`) with Claude Code definition only
4. Implement Metadata Pass (`metadata.ts`) for Markdown frontmatter + headings
5. Implement `serializer.ts` — build valid KitGraph from nodes (no edges yet)
6. Implement CLI entry point (`cli/index.ts`) — `repoviz analyze <path>`
7. Write unit tests for detector + serializer
8. Write integration test with `fixtures/claude-workspace/` fixture
9. Validate: `npx ts-node src/cli/index.ts ./fixtures/claude-workspace` produces valid JSON

### Phase B — Relationship Pass + remaining 5 harnesses

1. Implement Relationship Pass (`relationships.ts`) — regex/path scanning for `reads`, `executes`, `references`
2. Write harness definitions for: GitHub Copilot, Codex CLI, Gemini CLI, Cursor, Windsurf
3. Create fixture repos for each harness
4. Extend integration tests for all 6 harnesses
5. Implement multi-harness detection (run all definitions, aggregate)
6. Validate `harnesses{}` index populated correctly for multi-harness fixture

### Phase C — Performance, edge cases, validation

1. Implement parallel file I/O (async batch reads)
2. Add binary file detection (skip before read)
3. Add symlink guard (skip files resolving outside repo root)
4. Add >1 MB file skip
5. Add JSON schema validation of output against `kit-graph.schema.json`
6. Run performance benchmark: 500-file synthetic repo must complete < 5s
7. Add `--harness` filter option to CLI
8. Final integration test pass across all harnesses + multi-harness

## Key Design Decisions (from research.md)

- **Three-pass pipeline**: Detection → Metadata → Relationships (separated concerns, each independently testable)
- **Declarative definitions**: YAML files in `definitions/` — community can add harnesses without touching core
- **Canonical vocabulary + `native_type`**: engine normalizes, visualization can display native terms
- **Multi-harness support**: all definitions run in parallel; `harnesses{}` index enables UI filtering
- **Parallel async I/O**: file reads batched asynchronously for performance
- **No code execution**: zero eval/exec/spawn from analyzed repo content — enforced at architecture level
